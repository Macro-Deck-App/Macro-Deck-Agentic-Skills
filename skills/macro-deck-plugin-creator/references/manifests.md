# Manifests, build configuration and the AI statement

Two files describe a plugin: `manifest.json` (identity and publication metadata, read by Macro Deck
and the Creator Portal) and `macrodeck-build.json` (how the CLI builds each platform), both in the
plugin project directory. Exact fields come from the current manifest schema, not from this file.

## Sources of truth

- Manifest schema: `https://docs.macro-deck.app/schemas/plugin-manifest-v1.schema.json` (verify the
  response is JSON; the `$schema` host `schemas.macro-deck.app` used inside manifests has been seen
  to redirect to a web page). Fallback: the Macro Deck repository file
  `docs/public/schemas/plugin-manifest-v1.schema.json`. The schema marks
  every field with a requirement level (`runtime`, `publication`, `recommended`, `generated`);
  read the descriptions, they carry rules the type alone does not.
- Reference page: `/reference/manifest/`.
- Build manifest: no published schema at the time of writing. Derive keys from `/cli/build/`, the
  generated file and `macrodeck-plugin build --help`.
- Check mechanically: `macrodeck-plugin validate --level publication --artifact <packed file>`
  (run it on build output, not the project directory) and `scripts/check-plugin.py`.

Fetch the schema fresh each task and compare its property list with what you are about to write.
Unknown properties are tolerated by the host but do not rely on that: write only schema fields.

## Fields owned by tooling: do not hand-maintain

`files[]` and `signature` are generated by pack and signing. `languages` is derived from
`Localization/Strings.<culture>.resx` by `build`/`pack`. The version that ships is the release tag
(the publish workflow writes it into the manifest), so the in-repo `version` is informational; keep
it a valid SemVer and do not treat bumping it as the release mechanism.

## Consistency is a hard requirement

Compare both manifests and the project files before calling anything done. Every row must hold.
`scripts/check-plugin.py` checks most of them; check the rest by reading.

| Subject | manifest.json | macrodeck-build.json / project / repository |
| --- | --- | --- |
| Platforms | keys of `entrypoints` | keys of `targets` are identical; each target's `-r` equals its key; every key is a known runtime identifier; CI and release cover the same platforms |
| Executable name | `entrypoints.<rid>.executable` is `runtimes/<rid>/<Name>.dll` (framework-dependent) | project `AssemblyName` is `<Name>`; the published output contains it |
| Runtime kind | `runtime.kind` `FrameworkDependent` with `dotnetVersion` and a `.dll` executable | target passes `--self-contained false` and `-p:UseAppHost=false`; no self-contained property anywhere |
| Target framework | `runtime.dotnetVersion` | project `TargetFramework` (`net10.0` means `10.0`) |
| Publish project | n/a | the project named in each target's `arguments` exists next to the manifest |
| Output folder | `runtimes/<rid>/` layout | target `output` is the folder the publish command writes to |
| Icon | `icon` path exists | project copies it to the output (`Content` item), file is a real asset you may redistribute |
| Manifest copy | n/a | project copies `manifest.json` to the output |
| Identity | `id` (lowercase reverse-DNS, at least three dot-separated parts) | Creator Portal Package ID, generated `Strings` namespace and README use the same name; id and namespace follow the naming rules |
| Publisher | `publisher.name` | the Creator Portal owner (organization name, or username for a personal project, compared ignoring case) |
| Repository | `repository` is `https://github.com/<owner>/<name>` | the repository releases are built from; README links; no placeholder |
| License | `license` SPDX identifier | `LICENSE` file text is that license; the copyright holder is the real rights holder; incorporated code does not contradict it |
| Description, name | `description`, `name` | README title and summary, Store listing; not misleading, not implying official status |
| Compatibility | `compatibility.macroDeck` range | SDK version actually built against; the range must not claim support for hosts the SDK does not target |
| Permissions | `permissions` | only those the code needs; verify the vocabulary in the schema description |
| AI declaration | `ai` | what the plugin and its assets actually do, see below |
| Source for CI | n/a | release workflow `source` is the directory containing both manifests |
| Version | informational | release workflow takes it from the tag; CLI and SDK versions in CI and release are the resolved ones |

Placeholders that must never survive: `Example Publisher`, `https://github.com/example/...`,
`com.example.*`, `app.macro-deck.*`, template names and descriptions, "Macro Deck Contributors" as
copyright holder in a third-party plugin.

When a value changes in one file, search for it in the other and in README, workflows and tests in
the same change.

## Build configuration

Plugins are **framework-dependent**: Macro Deck ships the .NET runtime (including ASP.NET Core) and
runs the plugin on it. Do not publish self-contained.

- No `<SelfContained>true</SelfContained>` or `<PublishSelfContained>true</PublishSelfContained>` in
  any project, `Directory.Build.props`, `Directory.Build.targets` or publish profile.
- No `--self-contained true` or `-p:SelfContained=true` in `macrodeck-build.json`, CI or release
  workflows. No single-file, trimmed or AOT publishing unless the docs say plugins support it.
- Targets pass `--self-contained false` and `-p:UseAppHost=false`.
- Do not bundle runtime or framework assemblies the host provides. Inspect the publish output
  (`bin/publish/<rid>`) and the packed artifact (`macrodeck-plugin inspect --artifact ...`): it
  should contain the plugin's own assemblies and genuinely needed NuGet packages only. A package of
  tens of megabytes means something is wrong.
- Self-contained is allowed only for a runtime Macro Deck does not ship, and the Creator Portal
  refuses an upload that is self-contained on a platform the Project has no grant for. A grant needs a
  written justification of at least 80 characters approved by a moderator, and moderators treat an
  unjustified self-contained package as a blocker. It is the user's decision: stop and ask, record it
  in the report, and change all three places (entrypoint without `runtime`, apphost executable,
  `--self-contained true`) together.
- Package size: keep the package lean. Avoid large dependency trees and never bundle unneeded files
  (`macrodeck-plugin inspect` lists the entries). The Platform's 64-entry limit applies to the upload
  zip the official workflow builds, not to the package, so the workflow handles it.
- Never reference precompiled third-party DLLs (`HintPath`, `Reference Include=*.dll`).
- Cross-platform .NET code builds for all declared runtime identifiers from one Linux runner; only
  native or `-windows` targets need per-platform builds (see [release-workflow.md](release-workflow.md)).

## AI statement

The `ai` object declares AI involvement for the Store listing. Fields (verify in the current schema):
`interaction`, `generatedContent`, `generatedAssets` (booleans) and `services` (names of external AI
services). Rules established by the current schema description and the Creator Guidelines:

- Omitting `ai` means "not declared", which the Store shows as exactly that and never as "uses no
  AI". Always write the object explicitly. A plugin that uses no AI declares all three flags `false`
  and no `services`.
- Declare what the **package** is or does, per the guidelines:
  - `interaction`: users interact with an AI system through the plugin (chatbot, voice assistant,
    conversational agent).
  - `generatedContent`: the plugin generates images, audio, video or text with AI while running.
  - `generatedAssets`: the package ships assets created or substantially changed with AI: icons,
    images, sounds, texts.
  - `services`: display names of external AI services used. Naming a service counts as using AI.
- **The coding agent that wrote the source code does not by itself trigger a declaration.** The
  fields cover runtime AI and shipped assets, not how source code was authored. Do not set a flag
  merely because an agent helped implement the plugin.
- **Assets the agent created do count.** If the agent drew or modified the icon, an image, a sound
  or substantial user-facing text content shipped in the package, set `generatedAssets` to `true`.
  Ordinary localization strings that are part of normal UI code are not assets; a substantial
  AI-written or AI-translated text corpus, documents or store texts shipped to users is a judgment
  call: when in doubt declare, and tell the user why. A hand-supplied or properly licensed icon
  does not require it. Prefer to ask the user for an icon they have rights to, or a simple icon the
  user approves, and declare it accurately.
- Runtime AI features also bring Creator Guidelines duties: tell users they interact with AI,
  preserve provenance markers, label realistic synthetic media, disclose what data goes to which AI
  service in the README.
- State the derivation in the final report ("`generatedAssets` is true because the icon was created
  by the agent") so the publisher can correct the declaration. The Creator Portal has its own AI
  declaration; they must agree with the manifest.

Re-read the current guidelines section on AI and the manifest description each time; if either now
says something different from this summary, follow the source and report the change.
